# Kubernetes Dashboard: Interview Explanation

## A project explanation I can give in an interview

The project I worked on is a web-based Kubernetes dashboard. I chose this problem because Kubernetes is widely used to run applications, but understanding what is happening inside a cluster can be difficult, especially when an engineer is new to it. An operator may have to use the command line, inspect YAML files, open monitoring tools, and switch between several Kubernetes resources just to find out why one application is not healthy. My goal with this project is to make the common information and operations easier to reach from one interface, and to help explain Kubernetes problems in straightforward language.

The dashboard is built with Next.js and React. Next.js gives the project page routing and server-side API routes, while React is used to build the interactive screens. The application has pages for the cluster overview, workloads, pods, deployments, services, gateways, configuration, storage, nodes, namespaces, autoscaling, security, monitoring, topology, and AI workloads. A shared dashboard layout provides navigation and keeps common controls, including the chat assistant, available as the user moves between pages. Tailwind CSS and reusable UI components give the pages consistent controls and layout. Lucide React supplies icons, and Recharts is used for charts.

The data flow starts when a page loads or refreshes. The browser calls an API route belonging to the Next.js application. When the server has a Kubernetes configuration and demo mode is disabled, the route uses the Kubernetes JavaScript client to request resources from the Kubernetes API. The client can use a kubeconfig available to the server or the service account credentials mounted into a pod when the dashboard is running inside Kubernetes. The route then maps Kubernetes objects into a simpler JSON shape that the page can display. For example, the pods route turns pod metadata and status into fields such as pod name, namespace, phase, node, IP address, readiness, and restart count.

This separation is useful because the browser does not need direct access to the Kubernetes API or its credentials. The API server still checks the permissions granted to the dashboard identity through Kubernetes RBAC. The cluster context feature lets the application select among configured contexts, but the server still needs valid configuration and permission to reach each selected cluster. Some features also need optional Kubernetes APIs, metrics services, or custom resources to be installed and available in the target cluster.

The project also has a demo mode and fallback data. These are useful for exploring the interface without connecting to a real cluster, but they are not evidence that the dashboard has been deployed to production. It is important to explain this honestly in an interview: if demo mode is on, or the application cannot use Kubernetes credentials, pages can show sample values. Some display values are not yet backed by live telemetry; for example, the cluster overview route currently assigns fixed CPU and memory percentages. For a production monitoring dashboard, those values should come from a real metrics source, and the interface should clearly label any sample or estimated data.

Operators can use the dashboard to inspect resources and, where supported by the API and RBAC permissions, perform actions such as managing workloads. Other parts of the interface help inspect logs, configuration, storage, networking, cluster relationships, security findings, and GPU-oriented workloads. The topology view is intended to make relationships such as a gateway or ingress, service, deployment, pod, and node easier to follow. The xterm-based terminal and pod log views support more direct troubleshooting. These functions depend on the Kubernetes permissions and cluster features available to the application, so I would verify them against the target environment rather than assume every cluster exposes every feature.

I also added a conversational Kubernetes assistant powered by Google Gemini. The chat panel sends the recent conversation to a Next.js server route. That route validates the request, sends it to Gemini using a server-side API key, and streams the response back to the browser so the answer appears as it is generated. Keeping the provider request on the server means the Gemini key is not placed in browser JavaScript. The assistant can explain Kubernetes concepts and suggest diagnostic steps, but it does not read the live cluster or run commands. Its suggestions need to be checked by an operator, and users should not put credentials or confidential data in the chat.

The sign-in screen in this project is a demo, not production authentication. It stores demo authentication state in the browser, so it must not be treated as a security boundary for a publicly reachable deployment. Before using this project with real users in production, I would add trusted server-side authentication, enforce user authorization in the API routes, apply rate limits to the AI endpoint, and review the Kubernetes RBAC rules so the dashboard gets only the permissions it needs. I would also protect secrets, add auditing for changes, and use an approved network entry point rather than exposing an unprotected dashboard directly.

For development, I use Node.js and npm to install the dependencies and run the Next.js server. TypeScript helps catch type errors before deployment, ESLint checks code quality, and the production build verifies that Next.js can compile the application. Docker packages the built application into a repeatable image using a multi-stage Dockerfile. Docker Compose is available for local container use, and Kubernetes manifests describe a ServiceAccount, RBAC permissions, a Deployment, and Services for running the dashboard in a cluster. GitHub Actions automates linting, type checking, building, and image publishing workflows.

In summary, the project brings common Kubernetes inspection and management views into one web application. The browser presents the interface, the Next.js API routes shape requests and responses, and the Kubernetes client talks to the cluster using the permissions assigned to the server. Demo data makes it possible to learn the interface without a cluster, while the Gemini assistant provides explanations without taking control of the cluster. The next steps I would prioritize are production-grade authentication and authorization, least-privilege RBAC, reliable live metrics instead of fixed or sample figures, stronger tests for the API routes and resource actions, and clear indicators showing whether displayed data is live, estimated, or demo data.

## If the interviewer asks what I learned

This project helped me understand that a Kubernetes dashboard is not only a frontend. The server needs a safe identity, access to the Kubernetes API, carefully scoped RBAC permissions, and a way to translate Kubernetes objects into data the UI can use. I also learned that a visual interface must distinguish real cluster observations from fallback data, because otherwise a user could make an operational decision based on a number that only looks real. For an AI feature, I learned to keep provider credentials on the server, validate requests, stream responses, and be clear about what the assistant can and cannot access.

## Dashboard features and UI walkthrough

The dashboard brings common Kubernetes inventory, health checks, troubleshooting tools, and selected resource actions into one interface. The shared shell keeps navigation, search, cluster context, connection status, and the AI assistant available across the resource pages. Data pages call the application's API routes through the API client; an action that changes a resource still depends on the server's Kubernetes credentials, RBAC permissions, and the behavior of the specific API route.

### Shared dashboard shell

- **Sidebar navigation:** The sidebar has two groups. **Cluster Resources** contains Overview, Workloads, Autoscaling (HPA), Pods, Deployments, Services & Ingress, Gateway API, Custom Resources, Config & Secrets, Storage & PVs, Helm Hub, Nodes, and Namespaces. **Operations & Telemetry** contains AI & GPU Workloads, Security & CIS, Topology Map, Web Terminal, Monitoring, and Settings. The selected route is highlighted. The sidebar can collapse to icons and expand again.
- **Search:** The header search opens a local catalog of dashboard destinations. It filters the catalog by page name, category, description, or keywords; arrow keys move through results, Enter opens the selected page, Escape closes the list, and Ctrl+K or Cmd+K focuses the search. It is navigation search, not a query across live Kubernetes objects.
- **Cluster context:** The selector lists contexts returned by the server. Choosing a different context asks the server to switch and reloads the page. A context is only usable if the server has credentials and permissions for it.
- **Connection and demo indicators:** The connection badge starts in a checking state and, outside demo mode, checks cluster information periodically. It can show Connected, Disconnected, Checking, or Demo. Demo mode is also called out separately when enabled. A disconnected badge means the server could not reach the configured cluster; it does not mean the page's fallback or sample values are live data.
- **Issue shortcut and account control:** The bell icon jumps to the overview's Live Issue Monitor. The sidebar footer shows the demo operator identity and a sign-out action. The sign-in state in this project is browser-side demo authentication, not production identity or API authorization.
- **AI assistant:** A floating button opens a right-side chat panel on dashboard pages. Suggested prompts can be selected, messages stream into the conversation, Enter sends (Shift+Enter inserts a line break), and the conversation can be cleared. The assistant answers through the server-side Gemini route; it is not a live cluster query or command runner.

### Overview page

The Overview page assembles a quick operational picture rather than replacing the detailed resource pages:

1. **Cluster overview banner:** Shows the cluster connection/demo state, cluster name, Kubernetes version, and last successful refresh time. Refresh calls the cluster-info, pods, nodes, and services endpoints together. The page refreshes this summary every 15 seconds and offers a manual Refresh button. If loading fails, it shows an error and unavailable placeholders instead of presenting the failed request as healthy data.
2. **Resource summary cards:** Compute Nodes, Container Pods, Network Services, and Namespaces show counts. The node, pod, service, and namespace cards link to their corresponding detail pages. Ready-node and running-pod counts give a small health cue.
3. **Quick Actions:** Provides shortcuts for restarting a deployment, opening workload scaling, opening pod logs, requesting a cluster-state export, running a security audit, and cleaning completed/evicted resources. Some cards navigate elsewhere; others post an action to the server and show success or error feedback. These actions are not merely visual: verify the target, server implementation, and RBAC before using them on a real cluster. The restart shortcut currently targets a deployment named `frontend-app`.
4. **Sample Resource Allocation:** Shows cluster averages and per-node CPU, memory, disk, status, and pod-count bars. The node selector filters the detail rows. These values are hard-coded illustrative samples in the current implementation, not Kubernetes metrics.
5. **Live Issue Monitor:** Requests health-check results on load and every 15 seconds. It displays critical/warning totals, the check time, affected resource, explanation, and suggested next step, with a manual refresh control. It is advisory and does not mutate resources. In demo mode it shows a demo notice; failed checks show an error.
6. **Active Pods:** Lists up to five pods with namespace, node, phase/status, and IP, and links to the full Pods page. It has explicit empty and unavailable states.
7. **Activity Stream:** Shows recorded dashboard activity with action type, namespace, resource, message, and relative time. It loads on entry, polls every 10 seconds, and has a manual refresh button. It reflects the activity endpoint/session data, not a complete Kubernetes event history.

### Cluster resource pages

- **Workloads:** A combined workload hub with Overview, Deployments, StatefulSets, DaemonSets, Jobs, CronJobs, and Pods tabs. The overview summarizes controller groups; resource tabs expose their respective rows and status. Depending on resource type, available controls include scaling replicas, restarting deployments or daemonsets, triggering or suspending CronJobs, opening YAML, and deleting resources. Filters and namespace scope help narrow the list.
- **Autoscaling (HPA):** Lists HorizontalPodAutoscalers and their target workload, namespace, min/max/current replicas, metrics, and status. Namespace selection and text search filter the list; summary cards call out scaling and max-replica states. The YAML control opens an inspection view. The page loads on entry and can be refreshed manually.
- **Pods:** Lists pod health and details such as namespace, node, readiness, restarts, and container information. Search and namespace filters narrow the list; refresh/auto-refresh and export controls support operations. Per-pod controls provide details, logs or terminal entry, YAML inspection, restart, and deletion where implemented. Deleting or restarting affects the cluster.
- **Deployments:** Shows deployment totals, healthy/ready replicas, rollout status, and replica counts alongside a searchable/filterable table. It supports refresh, optional auto-refresh, CSV export, scaling, rolling restart, YAML inspection, and deletion, including selection-based bulk deletion where available.
- **Services & Ingress:** Separates Services and Ingresses into tabs, with counts for service types and ingress resources. Namespace selection and refresh load the lists. The tables support copying network addresses, viewing YAML, and deleting selected resources.
- **Gateway API:** Separates Gateway resources and HTTPRoutes into tabs. Namespace and text filters narrow gateways by name/class and routes by name/hostname/parent. Summary cards show gateway and route counts; YAML inspection is available. The Gateway API CRDs/controller must exist in the cluster for meaningful live results.
- **Custom Resources:** Discovers CustomResourceDefinitions and summarizes total definitions, API groups, scope, and established status. Search and API-group filters narrow the table; YAML inspection shows definition details. This page inspects CRD schemas/definitions, not a full editor for every custom-resource instance.
- **Config & Secrets:** Switches between ConfigMaps and Secrets, with namespace filtering and counts for configuration objects and TLS-related data. Detail inspection and YAML views are available; secret values can be revealed in the UI, and resources can be deleted. Treat the page as sensitive and use least-privilege access; avoid screenshots or exports containing secret data.
- **Storage & PVs:** Uses tabs for PersistentVolumeClaims, PersistentVolumes, and StorageClasses. Summary metrics and namespace selection help locate capacity and bindings. YAML inspection is available, and the current PVC/PV tables expose deletion actions. Deleting storage resources can risk data availability or loss; check reclaim policy and workload usage first.
- **Helm Hub:** Has Installed Releases and Marketplace tabs. Release rows expose revision/status information and actions to roll back or uninstall. The catalog supports selecting a chart and configuring an install. Chart availability and successful operations depend on the server implementation, Helm integration, cluster access, and permissions.
- **Nodes:** Summarizes node count/readiness, CPU capacity, and runtime, then lists node conditions and details. Refresh, optional auto-refresh, and CSV export are provided. The page also exposes node details/YAML, cordon/uncordon, and drain controls; these affect scheduling and running workloads.
- **Namespaces:** Summarizes namespace counts and active/system status, with refresh and export. Namespace rows can open details, show YAML, copy the name, and delete a namespace. Namespace deletion removes or disrupts the resources scoped inside it.

### Operations and telemetry pages

- **AI & GPU Workloads:** Presents accelerator inventory, allocated/free GPUs, VRAM, utilization, and model-serving workload rows with framework, task, GPU assignment, memory, throughput/latency, and status fields. GPU node cards include hardware model, temperature, and power figures. Refresh requests the AI workload endpoint. The completeness and freshness of these hardware/runtime fields depend on the available cluster integrations; verify their source before treating them as telemetry.
- **Security & CIS:** Shows an overall posture score and workload, network/TLS, and RBAC categories. Search, category and severity filters narrow findings; expanding a finding reveals impact and remediation guidance. The Run Security Audit control currently presents a short simulated scan delay and reloads the report; do not describe that button as a verified CIS scanner unless a real scanner is connected.
- **Topology Map:** Loads ingress, services, deployments, pods, and nodes to visualize resource relationships. Namespace filtering and manual refresh update the view; selecting a graph item shows its details. It is a navigation/inspection aid, and the relationships shown depend on the API data available to the page.
- **Web Terminal:** Select a pod and container, then use the xterm.js panel to submit commands through the server-side exec route. The first running pod is selected by default when possible, and the pod list can be refreshed. This is an interactive shell in a container, not a read-only dashboard; command access and impact are governed by the server's Kubernetes credentials and RBAC.
- **Monitoring:** Displays CPU, memory, network, pod-health cards, time-series charts, and a node capacity table, with a control to pause/resume chart updates and export a CSV. Important limitation: the current CPU, memory, and network chart points are generated with random values every four seconds; they are demonstration samples, not live metrics-server or Prometheus telemetry. Pod and node inventory is fetched from the API, but that does not make the generated chart data real.
- **Settings:** Groups general preferences, notifications, security/session options, and a masked API-token field. Language updates the language context; the visible controls let the user edit refresh interval, timezone, toggles, and cluster label. In the current page implementation, Save only shows a simulated saving/success state and Export downloads a JSON snapshot of selected settings; settings are not persisted to a server. The displayed token is a placeholder, not a secure token-management workflow.

### Sign-in and data interpretation

The sign-in page is an entry point for the demo account flow, with a convenience action to fill demo credentials. Authentication state is stored in the browser and is not a production security boundary. Across all pages, a populated card or chart is not by itself proof of live cluster data: demo mode, fallback responses, hard-coded samples, and generated chart points are used in parts of this project. Before operational use, confirm the data source and timestamp, validate action targets, and test permissions in a non-production cluster.
